- A§9.5 / item 6 (shadowing): plugin servers register as `plugin:<plugin>:<server>`. A user server of the same name with different args does not shadow them: both are listed and both start (VERIFIED). A user server with the plugin's exact command and args suppresses the plugin server, even with a different `env` (VERIFIED, two runs: plugin line present before, absent after). Tool names are `mcp__<name>__*` or `mcp__plugin_<plugin>_<server>__*`, so the `doctor` prefix check must accept both.
- A§9.4 / items 15, 20 (evals): `claude plugin eval --eval-dir` rejects an absolute path and `..` with a hard error, not a fallback (VERIFIED). `--mocks record` does not start a plugin server that has no mock, so the mail-reader evals need a mock under `evals/mocks/` (format UNRUN); real servers only with `--allow-real-servers` or `--mocks off`; a non-interactive run needs `--trust-plugin` (help text). Eval env allowlist: DOC. Keep evals in `plugin/evals/`. Real MCP servers start as the user, outside the OS sandbox, with the user's default config; reports publish to claude.ai by default; results are written under `<plugin>/<eval dir>/results/` (help text, DOC).
- A§9.7 / item 12 (Windows `command -v`): the Bash tool exists on Windows only with Git Bash; otherwise PowerShell is primary. Branch on the shell tool, or use `Get-Command uvx`. Status: see the table.
- A§9.7 item 19: `CLAUDECODE=1` is set in the Bash tool and in stdio MCP children (VERIFIED), and per docs in IDE terminals and hooks, so a `--stdin` refusal keyed on it fires there too. `CLAUDE_CODE_CHILD_SESSION` is set in the Bash tool (seen only in a subagent session) and was unset in the MCP child, but the launcher had it unset, so that is not evidence of what Claude Code adds (row 19).

## Decisions for A§10
- Item 4: keep `MCPServer`; drop the low-level fallback (in-memory and stdio both ran).
- Item 5: keep "`register claude-desktop` only" until a user confirms `type: uv` on Windows and macOS.
- Item 6: detect with `claude plugin list --json` (tolerate absent `claude`), then `installed_plugins.json`; match `id` prefix `mailferret@`, ignore `@builtin`; report scope and `projectPath`; `enabled` is per id for the cwd. A manual server with the plugin's exact command and args suppresses the plugin server (env ignored), and one with different args runs alongside it. `doctor` accepts both tool-name prefixes (`mcp__mailferret__*`, `mcp__plugin_mailferret_mailferret__*`) and reports duplicates.
- Item 11: keep "a `uvx` hit is inconclusive" in `doctor`; the Bash half stays DOC.
- A§9.7 agent `tools`: the eight `mcp__plugin_mailferret_mailferret__<tool>` names enumerated, no wildcard, no `Read`; add `disallowedTools: Skill, Agent`. Skill `allowed-tools`: exact pinned Bash strings, no `:*`. Runtime checks (items 17, 18) are UNRUN: P3 (T-04, T-18) must assert the agent's runtime tool list excludes Skill, Agent and every non-`mcp__plugin_mailferret_mailferret__*` tool, with the user's manual `/smoke-test` as backstop (PLAN edit tracked in #7). P2's CI parity test checks the file only.
- Item 12: `doctor` branches on the available shell tool (POSIX `command -v` vs PowerShell `Get-Command`).
- Item 13: no `--print`-only fallback; `register claude-code` uses `claude mcp add-json`, backing up the scope's file first.
- Item 14: Cowork stays unsupported ("unverified") until a user checks; the DOC statement is not enough.
- Items 15/20: evals live in `plugin/evals/` with mocks (format UNRUN; `--mocks record` needs a mock under `evals/mocks/`); never depend on injecting `MAILFERRET_CONFIG`. The `--eval-dir` flag must be a relative path inside the plugin. Invocation: `--mocks record` without `--allow-real-servers`, never `--mocks off`; `--no-publish`; `--output-dir`, `--report` and `--json` paths outside `plugin/` (`--output-dir` moves only `aggregate-result.json`); gitignore `plugin/evals/results/` and keep it out of the shipped plugin; never `--scaffold`; `--allow-tools` only the eight `mcp__plugin_mailferret_mailferret__<tool>` names (never Bash, WebFetch, Write, Edit). The T-18 injection fixture is synthetic `example.com` with no live URL; whether it ships in the cache or is generated at eval time is decided in #7. Pins tracked in #7.
- Item 16: `${CLAUDE_PLUGIN_ROOT}/constraints.txt` in `args` with `--constraints` (short `-c`); `--exclude-newer` as an additional pin.
- Item 19 (T-20): refuse `--stdin` when either `CLAUDECODE=1` or `CLAUDE_CODE_CHILD_SESSION` is set; best effort. `CLAUDECODE=1` also appears in IDE terminals and hooks (DOC), so a human piping a secret there is refused too: an accepted false positive (use the TTY prompt). `CLAUDE_CODE_CHILD_SESSION` is unverified at top level and may add nothing.
- Item 21: use the documented paths; `--desktop-config <path>` is mandatory where unverified (MSIX).
- Item 22: use a generated Linux-side launcher script at a space-free absolute path, run via `--exec`. `registration/` writes it under T-12 (backup, atomic write, owner-only mode, no group- or other-writable parent) and `doctor` checks its mode as for the config (T-11); tracked in #7.
- Item 9: ship zip-upload instructions for claude.ai; keep Cowork "unverified" until the user checks.
