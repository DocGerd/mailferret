# mailferret security design

Implements R§9 and R§11 (`R§n` = a section of `docs/REQUIREMENTS.md`, `A§n` = `docs/ARCHITECTURE.md`, bare `§n` = this file). Threat IDs (`T-nn`) and limit IDs (`L-nn`) are stable: PLAN tasks and the review gate cite them.

## 1. Assets

| Asset | Property to protect |
|---|---|
| IMAP credentials | confidentiality |
| Mail content and metadata | confidentiality; faithful (not silently altered) presentation |
| Mailbox state (flags, folders, messages) | integrity: nothing changes in this version, not even `\Seen` |
| Client config files (Claude Code, Claude Desktop) | integrity and availability |
| The user's machine | availability (no OOM, no hang) |

## 2. Trust boundaries

| ID | Boundary | Trust |
|---|---|---|
| B1 | MCP client / model → server tool inputs | untrusted: the model may itself be steered by injected content |
| B2 | Server ↔ IMAP server | network: TLS-authenticated, but the server's responses are still validated and bounded |
| B3 | Mail content (any sender) | hostile |
| B4 | Server ↔ credential backend (keyring, user command) | trusted store, untrusted availability (may be locked or hang) |
| B5 | Local files (mailferret config, client configs) | same-user, may be tampered with by other local tooling |
| B6 | Supply chain (PyPI, uvx cache, plugin marketplace) | pinned and verified |
| B7 | Plugin components inside Claude Code | defense in depth only, never the enforcement point |

Out of scope: malware running as the same user with full access (it can read the keyring directly), and a compromised OS or Python runtime.

## 3. Read-only guarantee

Enforced in the server process (`imap/`, A§6), independent of any client, hint or hook:

- R1: a command-verb allowlist, vetted on the first `send` after `_new_tag` arms the guard (A§6); any other verb raises `ReadOnlyViolation` before a byte is sent, with a fixed reason and never the line's bytes (the line may be a LOGIN). Later `send`s pass a fail-closed gate: literal bytes only after this tag's `+`, AUTHENTICATE replies matched with `fullmatch`, and the gate closed by the tagged completion. `{n+}` (LITERAL+) is refused whether or not the server advertises it: its bytes would leave before the server accepted the announcing line, so a server that rejects the line would read them as a command. The refusal is the guarantee; `ReadOnlySession` also hides `LITERAL+` from imapclient (`has_capability`), only so that imapclient sends every literal synchronously.
- R2: a FETCH-item allowlist (`BODY.PEEK[...]`, never `BODY[`/`RFC822`/`RFC822.TEXT`). The armed line contains no CR/LF before its closing CRLF and ends in CRLF; only SEARCH, SORT and THREAD may be unterminated or announce a literal; `_new_tag` refuses to re-arm mid-command. So no fragment or literal can complete a half-sent FETCH.
- R3: folders are opened with `EXAMINE` only.
- R4: write/SMTP exist only as interfaces (A§2.5), with no implementation; the config schema rejects enabling them; the registered tool set is asserted exactly (A§2.5).
- R5: the hooks fail closed when imaplib or imapclient change. A§2.2 defines the required hook set and its checks once. Before the first connection in every process (`serve`, `setup`, `doctor`), `imap/` checks the set's methods and `_MAXLINE` and refuses to connect on a miss or a changed shape. On every connection, before LOGIN, the session asserts that each hook ran (greeting, CAPABILITY, STARTTLS probe); for the session's life every `{n}` literal must go through the hooked `read(n)`, `readline` enforces `L-20` itself, and a tagged completion for a tag whose command line the guard never vetted aborts the session. Any unmet check aborts the session with a typed error that is never reconnected (A§2.2). These checks detect a bypass only after the fact: the bypassing command's bytes have already left. The greeting, CAPABILITY, tripwire and STARTTLS checks guarantee that no LOGIN follows a session whose hooks did not run. The `read(n)` and `L-20` checks fire at the first literal or over-long line, after it has been read, so on a minor that bypasses them the literal caps, the `L-20` overshoot and the `L-26` total do not bound that first read; the every-minor tests (PLAN §3.3) are the guarantee there.

Verification: a recording fake IMAP server drives every tool and option and compares the wire with the allowlist, not with the guard's log (`test_guard_wire`). Send-gate tests (D2), each raising before a byte is sent: a bare tagged line through `send`; a line break inside the armed line; the fragments `UID FETCH 1 (FLAGS` then ` BODY[])`; a literal inside a FETCH, spaced and unspaced (`({n}`, `({n+}`), sync and `{n+}`; a `{n+}` announcement in a SEARCH, with and without `LITERAL+` advertised; `_new_tag` mid-command; literal bytes before `+` and after a tagged BAD; bytes after a completed AUTHENTICATE. The issue #7 probe, a SEARCH whose literal carries `UID STORE … \Seen`, never reaches the wire as a command: as `{n+}` it raises before any byte, and as a sync literal answered by a tagged BAD its bytes raise unsent. A LOGIN line with an embedded CRLF raises a `ReadOnlyViolation` that carries none of its bytes. On a fake server that advertises `LITERAL+`, an 8-bit SEARCH completes, its literal sent synchronously and only after `+` (the `has_capability` hide). R5: removing or reshaping each method of the set, or `_MAXLINE`, makes `serve`, `setup` and `doctor` refuse to connect (E3, E4, E5); removing one of `_readbuf` and `file.peek` does not, and removing both fails a STARTTLS upgrade before LOGIN. One stub per hook bypasses it; each aborts the session with no LOGIN on the wire: the greeting read around `readline`, a command line written straight to the socket, `_command_complete` skipped, STARTTLS without the probe, a `{n}` literal read without `read(n)`, and a `readline` that ignores `_MAXLINE`; the `{n}` and `_MAXLINE` stubs abort the session at that literal or line, before any further command. The line-break check runs on every minor as a stub-based test of the mixin; the wire-level embedded-CRLF test is meaningful only below 3.13 (imaplib refuses control characters itself from 3.13), so the CI matrix keeps both. A GreenMail test snapshots `FLAGS` and message counts for every folder before and after the full tool suite and asserts equality (`test_no_mutation`). Unit tests assert that `ReadOnlyViolation` is raised for every denied verb (`test_guard_denies`).

## 4. Threats

### Credentials

**T-01 Credentials at rest.** Mitigation: only in the platform keyring or behind the user's `command` backend; config keys named like secrets are rejected by the schema; registration never writes `env` secrets; on WSL the decided default is GPG-encrypted `pass` (V3, A§10 item 7); plaintext keyring backends are refused. Verification: a schema test rejects `password`/`token`/`secret` keys and any `credential_command.env` name outside the allowlist (A§2.1); a backend-detection test refuses fail, null and plaintext backends; a registration test asserts that written JSON contains no value taken from the test secret.

**T-02 Credentials in memory.** Mitigation: the secret is fetched only at login, held in a `Secret` wrapper (redacted `repr`/`str`), passed to `login`, then the reference is dropped. Python cannot zero strings, so this is best effort: no caching of the secret across reconnects beyond the backend itself, and no secret in exception arguments. imaplib's ASCII encoding of `LOGIN` raises `UnicodeEncodeError` with the secret in `args`, so `LOGIN` gets `str` only after an `isascii()` check on login and secret; non-ASCII goes to `AUTHENTICATE PLAIN` (UTF-8) when advertised, else a typed credential error raised outside any `except`, so no `__context__` holds the original (A§2 `auth/` row; for a non-ASCII login this is the default, pending D3). The keyring probe and `command` backends hand the secret back over a pipe (T-03, T-17). `credentials/` accepts it only from a process that exited 0 with every reader at EOF, and only if, once one trailing line ending (`\n` or `\r\n`) is stripped, it is not empty and no CR, LF or NUL remains. Anything else (a timeout, an empty result, a multi-line `pass` entry with `login:` or `url:` lines, a secret containing CR or LF) is `timeout` or a fixed-text `error`: every buffer is discarded and nothing is sent (A§2.1). `auth set` and `setup` refuse, before any spawn, a secret that this rule or `L-22` would refuse on `get`. Residual risk: the logging redaction set (T-03) keeps the secret and its encoded forms for the process lifetime, so a memory dump of a running server reveals it. Verification: `repr`/`str`/f-string/`logging` of `Secret` yield `***`; a test asserts no exception raised from `auth/` carries the secret in `args` or `__cause__` text; on the `imap/` login path, a non-ASCII secret is absent from the exception's args, repr, str, traceback and `__context__`, and from captured output; a multi-line `pass` entry and a secret containing CR or LF are refused, and none of their bytes reaches the wire, an exception or a log record; an empty result (exit 0 with empty stdout, or a bare line ending) is refused with the fixed-text `error` and sends no login; `auth set` and `setup` refuse an empty secret, one containing CR, LF or NUL, and one over `L-22`, and spawn nothing.

**T-03 Credentials in logs, errors and tool output.** Mitigation: logging goes to stderr only. imapclient logs commands and the username, and sets `debug` after construction, so its `debug` is a property that reads 0 and ignores sets, and the `imapclient` logger is pinned at `CRITICAL + 1` with `propagate = False` and a `NullHandler`; a WARNING pin is not enough (A§2.2). A redaction filter replaces every value in the process-wide redaction set before formatting. The set holds three forms per secret: raw, IMAP-quoted (`"` and `\` backslash-escaped, as LOGIN sends it) and the base64 of the `AUTHENTICATE PLAIN` blob (`\0login\0secret`); any `LOGIN`/`AUTHENTICATE` line, and every continuation line while an AUTHENTICATE is in progress, is redacted whole. Typed credential errors carry no secret (R§11). Tool errors map to fixed codes. A credential subprocess (the keyring probe, a `command`) returns the secret on stdout only: capped at `L-22`, a minimal env, never in its argv or env, and its stderr (`L-28`), which may contain the secret, and the gpg status channel (`L-29`), which carries key user IDs, never leave the classifier: not logged, returned or put in an exception (A§2.1). Verification: `test_login_redaction` logs at DEBUG during logins with a known secret containing `"` and `\` (the LOGIN leg on GreenMail; the AUTHENTICATE PLAIN leg on the D0 fake server, since GreenMail rejects PLAIN, V2), and asserts that none of the three forms appears in captured stderr or in any tool result; a Hypothesis property test feeds generated secrets through every error path; a fake probe and a fake command that write the secret to stderr leave it out of every log record, result and exception.

**T-16 Lockout by repeated login.** Restarts, new client sessions and a second client each start their own server process, so "no retry" must hold across processes. Mitigation: an explicit server rejection of LOGIN/AUTHENTICATE (tagged `NO`/`BAD`; timeouts, TLS and network errors do not count) writes an auth-failed marker for `<login>@<host>` to the data dir; while it exists, every process returns `auth_failed` naming `mailferret auth set <account>` (or `auth retry <account>` for a secret changed outside mailferret) without connecting; only those commands and `setup` clear it. A failure during the login phase (a drop or timeout after LOGIN/AUTHENTICATE was sent, before its tagged response) ends the call with `timeout` or `server_error`, is never followed by a reconnect (A§2.2) and sets no marker (default, pending D3). Mechanism choice uses the post-TLS capabilities (A§2 `auth/` row): `LOGIN` unless `LOGINDISABLED`; else `AUTHENTICATE PLAIN` if `AUTH=PLAIN`; else `auth_failed` before `credentials/` is touched; a non-ASCII secret also takes `AUTHENTICATE PLAIN` or a typed credential error (T-02), and so does a non-ASCII login (default, pending D3). Residual risk until D3 decides: an indeterminate outcome sets no marker, so a server that answers a bad password by dropping the connection or never answering gets one login per tool call and per process. Verification: against GreenMail with a real user (auth enabled) and a wrong password, exactly one login command appears on the wire across repeated tool calls in two separate server processes; fake-server cases for each mechanism branch (LOGIN; `LOGINDISABLED` + `AUTH=PLAIN` uses AUTHENTICATE; `LOGINDISABLED` without `AUTH=PLAIN` never calls the backend `get`); a fake server that drops the connection after reading LOGIN, and one that never answers it, each see exactly one login command in that call.

**T-17 Credential subprocess abuse or hang** (the `command` backend and the keyring probe). Mitigation (A§2.1): argv only (no shell), an absolute executable path resolved at setup, a fixed `cwd` and minimal env (the probe also gets `PYTHON_KEYRING_BACKEND` and `XDG_CONFIG_HOME`), the probe started as `sys.executable -I -m …`, a write's secret fed to stdin by a daemon writer under the same deadline, the whole process tree bounded by `L-14` (`command`) or `L-27` (keyring probe) with a new session + `killpg` on POSIX and a `ctypes` job object on Windows (unverified, A§10 item 23), daemon readers with bounded joins, stdout capped at `L-22` while reading and accepted only under the T-02 rule, stderr (`L-28`) and the gpg status channel (`L-29`) kept for the classifier only. `killpg` reaches same-session descendants only; one that calls `setsid` escapes it and may hold the pipes, so the return never waits for the readers: a kill at the deadline, or any reader not at EOF at the return, yields `timeout` and discards every buffer, so partial output is never used as a secret (T-16). `keyring` is not bounded in-process (`get_keyring()` hung on a mute session bus, V3), so no mailferret process calls it in-process: backend detection, the D-Bus error mapping and every lookup or write run in the probe, for `serve`, `doctor` and `auth set` alike, after the bus-address pre-check that refuses every transport but `unix` (A§2.1). The process rules have Linux and WSL evidence only (V3), and the probe has not run yet (B4); macOS and Windows are A§10 item 23. A pinentry is spawned by gpg-agent outside the tree, so the `pass` recipe sets `--pinentry-mode=error` (verified at the `pass`/gpg level, A§10 item 7) and classifies `locked` from gpg status codes on a channel separate from stderr. Residual risk: a `setsid` descendant survives the kill. Verification: tests with a fake command that sleeps, prompts, prints megabytes, writes the secret to stderr, leaves a same-session grandchild holding stdout past the deadline, or calls `setsid` while holding stdout, and a `set` child that neither reads its stdin nor exits; each returns within its bound plus a small margin with `timeout` or `limit_exceeded` and no secret, and no same-session process is left behind. A fake command writing megabytes to stderr and to the status channel, and a fake probe writing megabytes to stderr, keep memory bounded, give the classifier at most `L-28`/`L-29` bytes and return within their bound. A `keyring.py` planted in the data dir (the probe's `cwd`) is never imported by the probe. A locked `pass` store reads `locked` through the real spawn path. Bus-address pre-check tests: unset; `unixexec:`, `autolaunch:`, `tcp:`, `nonce-tcp:` and `launchd:`; a `;` list mixing accepted and refused entries, where only the accepted ones reach the probe; a `unix:` entry with neither or both of `path`/`abstract`; a missing `path`; the listen-only keys; and a raw `FileNotFoundError` or `TimeoutError` inside the probe reported as `unavailable` (V3-4, V3-5). The probe's bound is claimed as tested only with a retained mute-bus repro (B4). The Windows equivalents of the grandchild and `setsid` tests are A§10 item 23.

### Mail content

**T-04 Prompt injection via mail content** (subject, body, headers, display names, attachment names and text, hidden HTML text). The server cannot stop a client from obeying injected text; it makes content unmistakably data and removes hidden channels. Mitigation: every mail- or server-derived string is an `Untrusted` field and is wrapped in delimiters, with the escaping rule of A§2.4; hidden HTML content (`display:none`, `visibility:hidden`, `hidden`, zero font size, comments, `<head>`, `<script>`, `<style>`) and `Cf` controls (bidi overrides, zero-width) are removed and noted; the server `instructions` state that content is never instructions; the plugin `mail-reader` agent removes exfiltration tools from the reading context (unverified at runtime until P3 asserts the agent's tool list, A§10 item 18). Residual risk: a client that obeys content can still act on it (T-18), and the `mail-reader` agent's summary is itself a channel into the parent context; its output contract (instructions reported as quoted speech, URLs defanged) reduces but does not close it. Verification: corpus fixtures with injection text in each field; tests assert wrapping, that a mail containing the closing delimiter cannot terminate the block, that hidden spans are removed and noted, and that controls are stripped. P3 asserts the `mail-reader` agent's runtime tool list: no Skill, no Agent, nothing outside `mcp__plugin_mailferret_mailferret__*`; the user's `/smoke-test` is the backstop.

**T-18 Exfiltration through the client.** Private data, untrusted content and outbound tools in one context. Mitigation (outside the server's control): document the risk in the README; the plugin agent's enumerated tool allowlist removes outbound tools from the reading context (unverified at runtime until P3 asserts the agent's tool list, A§10 item 18); no tool ever fetches URLs or remote images from mail (`inscriptis` makes no network calls; images are never resolved). Residual path: the agent's summary returns to a parent that has Bash and WebFetch, so injected text that survives summarization can still steer an outbound call there; the output contract (defanged URLs, quoted instructions) is the only mitigation on that path. Verification: a test asserts no socket other than the IMAP connection is opened while processing the corpus (socket monkeypatch); a plugin eval (mocks only, in the isolated run of A§9.8) feeds a synthetic injection mail, generated at eval time and asking only for a harmless canary output, through `mail-reader` and asserts the summary quotes rather than follows it and contains no live URL.

**T-05 Oversized or malicious MIME** (multipart bombs, deep nesting, huge headers, many attachments). Mitigation: `RFC822.SIZE` is checked before any body fetch (R§11); BODYSTRUCTURE is bounded by depth `L-06` and part count `L-07`; headers are bounded by `L-05` and `L-04`; only selected parts are fetched, each partial-fetched to `L-02`; attachments listed up to `L-18`; each part is parsed in its own try block (per-attachment fault isolation, R§11). Verification: generated fixtures (at test time, not committed): 10,000-part multipart, 1,000-deep nesting, a 10 MiB header, a part declaring a 2 GiB size, a malformed boundary; tests assert bounded memory (`tracemalloc` peak under a budget) and a `limit_exceeded` note.

**T-06 PDF and attachment-parser DoS** (decompression bombs, recursive object graphs, page-count bombs). Mitigation: only attachments `≤ L-08` are fetched; `pypdf` runs in a subprocess (`python -I -m mailferret.content.pdf_worker`) with a wall time (`L-10`) and, per OS, a memory limit: `RLIMIT_AS` on Linux (verified, V1); on Windows an own `ctypes` job object (no pywin32); on macOS `RLIMIT_AS` may not be enforced. The Windows and macOS behaviour is open for C4 on windows and macos CI runners; where no memory limit holds, the bound is the wall time plus the page and decompressed-bytes caps (A§10 item 10). The worker lowers to `pdf_stream_bytes` every integer pypdf `Configuration` field whose default exceeds it, found at runtime with `dataclasses.fields` (the V1 note lists them for the version it ran), and derives the `page_tree_maximum_*` fields from `L-09`. It sets every `Configuration` field that names an external program to `None` before parsing: `jbig2dec_binary` defaults to `shutil.which("jbig2dec")`, and pypdf runs that native decoder on a `/JBIG2Decode` stream with no timeout and the worker's env, so with `None` such a stream becomes a per-attachment note and no process is spawned. The `PdfReader` constructor limits (`root_object_recovery_limit`, `xref_stream_maximum_entries`, `xref_rebuild_maximum_entries`) keep pypdf's defaults, under the wall time. pypdf has no page or text cap, so the worker loops pages up to `L-09` and caps extracted chars at `L-03`; `LimitReachedError` maps to `limit_exceeded`; no `pypdf` extras and no system decoder binary. Verification: generated PDF bombs (a deflate bomb stream in a complete page, since a page without `/Resources` silently returns empty text; 100,000 pages; a cyclic page tree) end with `limit_exceeded` within the timeout on every OS; a test fails if any integer field of the applied `Configuration` exceeds `pdf_stream_bytes`, or any field typed `str | None` is not `None`, so a new length or program field is caught; with a fake `jbig2dec` on `PATH` that records each run, a PDF whose content stream is `/JBIG2Decode` spawns no process and yields a note; the worker memory cap is asserted on Linux, and on Windows and macOS once C4 has established it.

**T-19 Charset and encoding attacks** (mislabelled charsets, invalid UTF-8, overlong sequences, encoded-word abuse). Mitigation: the decode chain falls back to `errors="replace"` (R§11); truncation never splits a codepoint, and an incomplete tail from a partial fetch is dropped; header decoding is bounded. Verification: corpus fixtures (PLAN §3.1) plus Hypothesis property tests (dev-only dependency, survey) over arbitrary bytes, charset labels and encoded words that assert no exception, valid `str` output and length within the limit.

### Network and server

**T-07 TLS / STARTTLS downgrade and certificate failures.** Mitigation: implicit TLS or STARTTLS only, no plaintext mode; STARTTLS that is not advertised or fails is a hard error, never a fallback; all pre-TLS capabilities are discarded and CAPABILITY is re-issued after the upgrade; any data the server sent before the TLS handshake completed is treated as a protocol error; verification always on with a TLS 1.2 minimum; `ca_file` is added with `load_verify_locations()` on top of the system store (A§2.2). imaplib's `starttls()` neither detects nor reliably discards pre-handshake bytes, so a guarded `_command_complete` probes the client read buffer by feature, then the kernel buffer (`MSG_PEEK`), before the wrap; bytes arriving after the probe fail the handshake (A§2.2). Verification: a fake server that omits STARTTLS, strips it, injects a pipelined response before the handshake, or presents a self-signed or wrong-host certificate; each must fail without sending `LOGIN`. The injection test runs on every supported Python minor in CI, since buffering differs between minors. GreenMail has no STARTTLS, so the positive STARTTLS path runs on the fake server only; GreenMail's plaintext port is a real-server "STARTTLS not advertised" case: a hard error, no `LOGIN` on the wire, the credential backend `get` never called (V2). A GreenMail test with its self-signed certificate fails without `ca_file` and passes with it, through mailferret's own TLS context builder.

**T-08 Malicious or compromised server responses** (lying `RFC822.SIZE`, ignoring partial ranges, huge literals, endless lines, malformed FETCH, changed UIDVALIDITY, hostile folder names). Mitigation: limits are enforced on read, not only requested. Every response byte, lines and literals, counts against the command's response total (A§2.2: per fetched message its literal cap plus the `L-20` line allowance, plus one more allowance, clamped to `L-26`); the line bytes alone are bounded separately by `L-32`, so a flood of lines that parse into far larger objects stops at `L-32` while `L-26` stays the total of lines and literals. Each line is also charged a fixed per-line overhead for the objects imaplib keeps per untagged line, so the total bounds what imaplib keeps, not only wire bytes, and a flood of short untagged lines is bounded too; `untagged_responses` is reset in `_new_tag`, so unconsumed entries do not pile up across commands. A literal over the command's literal cap (`L-05`, `L-02`, `L-08`, `L-01`), or one that would pass the total, aborts before any of its bytes are read. Lines are bounded at `L-20` plus a bounded overshoot, not before buffering: `imaplib._MAXLINE` is set once from `L-20`, process-global, and checked after the read; the `readline` hook also checks every line it returns. `L-20` is never raised to fit a response; searches run over windowed UID ranges (A§2.6). Each of these breaches is hostile: a typed breach error, never imaplib's `abort`, discards the session and fails the call, with no reconnect (§5). Response parse errors become `server_error` for that message only; UIDs are validated as positive ints; UIDVALIDITY is checked against every `message_ref`; folder names are `Untrusted`. Verification: fake-server scenarios for each case, with a memory budget asserted: an over-cap literal is never pulled; literals each under the cap whose sum crosses the total abort on the crossing one; a flood of short untagged lines with distinct types, each under `L-20`, aborts at `L-32` within the memory budget in one command, and spread over several commands stays within it; a breach, an `L-11` and an `L-12` timeout, and the `L-13` shutdown each give one connection attempt and at most one LOGIN in that call, with no connection used after the deadline (a socket opened by an uninterruptible DNS or connect call is closed unused, nothing sent); a FETCH response at its total made of dense short tokens (such as `FLAGS (\a \a …)`), parsed by imapclient, stays within the memory budget (D2 sizes `L-32` and the budget from this test); an over-long line raises within `L-20` plus the overshoot the test asserts (V1), discards the session and fails the call with `limit_exceeded`; a match set larger than one window yields no response line over `L-20` and results that are complete or `truncated`; a batch sized by the batch layer with every message at its literal cap completes.

**T-09 IMAP injection via tool inputs** (search terms, folder names, alias patterns). Mitigation: criteria always go to imapclient as a list, never a raw string; folder names are validated against the LIST result before EXAMINE; wildcards are matched client-side only. Verification: inputs containing `"`, `)`, CRLF and `{n}` literals produce exactly one well-formed command on the recording fake server.

**T-10 Accidental mutation.** See §3.

### Local files and supply chain

**T-11 Config file tampering.** Mitigation: on POSIX, `doctor` warns if the config or its directory is writable by group/others, and if the WSL Desktop launcher script (A§9.6) is not owned by its `-u` user or it or its parent directory is group- or other-writable; the schema rejects unknown keys and secrets; credentials are bound to `<login>@<host>` (A§2): for `keyring` through the entry key, for `command` through the binding record written by `auth set` and checked before `get` runs. A tampered host or login therefore finds no secret instead of sending it elsewhere, until the user re-runs `auth set`. `doctor` reports `ca_file` and the configured credential argv. Residual risk: whoever can write the config can set `credential_command` to any program, which is code execution as the user (same-user, out of scope per §2); an attacker who rewrites both the config and the binding record defeats the binding. Verification: for each backend, a test changes `host`, then `login`, and asserts that no secret is returned (`keyring`: the lookup under the new key finds nothing; `command`: `get` is never run) and no login command is sent; `doctor` warns for a launcher script with another owner, a group-writable script and a group-writable parent.

**T-12 Registration-file tampering or clobbering.** Mitigation: a timestamped backup next to the target (mode 0600 on POSIX), then an atomic write (temp file + `os.replace`), with unknown keys preserved and the file re-parsed after writing; invalid existing JSON aborts without writing; only the `mailferret` entry is touched; absolute launcher paths only. For `register claude-code`, which writes through `claude mcp add-json`, the same backup is taken of the file that scope writes before the CLI runs (A§9.5). The WSL Desktop launcher script (A§9.6) is written the same way (backup, atomic write): `#!/bin/sh` and one `exec` line with every argument `shlex.quote`d, no env and no secret, owned by the `-u` user, neither it nor its parent directory group- or other-writable. Verification: tests with a malformed file, a file with other servers, a read-only file, and a concurrent modification (mtime check before replace); for the CLI path, a fake `claude` executable asserts the backup exists before it is invoked; for the launcher script, its owner and mode, a refused group-writable parent, and its `exec` line with a space and a shell metacharacter in the `uvx` and constraints paths.

**T-13 Supply chain.** Policy: R§10 and the survey. Mitigation: `uv.lock` committed and checked in CI (`uv lock --check`); a dependency audit (OSV-based) on the lock in CI and on a schedule; Dependabot; `mcp>=2.3,<3`; no optional extras (`inscriptis[web-service]`, `pypdf[full]`); the heavy `mcp` transitive tree (HTTP server stack, JWT, crypto) is accepted but tracked: the audit covers it and stdio never starts the HTTP transport; releases use PyPI trusted publishing with attestations; the plugin pins an exact version. uvx ignores `uv.lock`, so plugin and `register` launches pass `--constraints` with a file generated by `uv export` from the release's lock (A§9.2, A§9.4): users get the exact audited transitive set (`--constraints` applies to the `--from` tool environment, verified in V4, A§10 item 16). Residual: the pin freezes transitive fixes until the next mailferret release, so a scheduled audit runs on the shipped constraints file and a hit triggers a patch release. Verification: CI jobs; a check that `plugin/constraints.txt` equals the export of the pinned tag's lock; a test asserts the server starts with only the stdio transport.

**T-15 Plugin hooks fail open; plugin components bypassed.** Mitigation: no security property depends on a plugin hook or skill (hooks fail open on timeout or crash, and `allowed-tools` only pre-approves). The only plugin-side containment is the agent's enumerated `tools` allowlist plus `disallowedTools: Skill, Agent` (A§9.7), and it is defense in depth: nothing forces delegation to the agent. Verification: the read-only and redaction tests run against the bare server, with no plugin present; a CI test asserts the agent's `tools` equals the server's registered read tools (so a future write tool is never granted) and that `disallowedTools` names Skill and Agent; P3 asserts the runtime tool list (T-04).

**T-20 Secret entry through the model.** A user pastes a password into chat, or an agent pipes one into `auth set` via its Bash tool. Mitigation: there is no setup skill; `auth set` and `setup` refuse a non-TTY stdin unless `--stdin` is given (checked before `getpass`, which otherwise silently falls back to stdin); `--stdin` is refused when `CLAUDECODE=1` or `CLAUDE_CODE_CHILD_SESSION` is set (a speed bump: an agent can unset them; `CLAUDECODE=1` also refuses a human piping a secret in an IDE terminal or hook, an accepted false positive, A§9.3); `not_configured` tool errors give the terminal command and say never to paste a password into the chat. Verification: CLI tests with a pipe for stdin (refused), `--stdin` with neither, either and both variables set, and a tool-error text test.

**T-21 Mail content in logs.** MCP clients persist server stderr (per-server log files), so whatever mailferret logs lands on disk outside the mailbox's protection. Mitigation: no log record contains a mail-derived string (subject, address, display name, folder name, body, attachment name) at any level; records carry account ids, UIDs, sizes, durations and error codes only; `ToolError` texts (logged by the SDK at INFO) follow the same rule. imapclient's own loggers carry server lines and warn with raw 8-bit server bytes, so they are pinned off (T-03); an imapclient `Address` is never stringified (addresses are formatted in `content/`); imaplib/imapclient exception messages and tracebacks carry server text (folder names, NO/BAD texts), so they are never logged or formatted and map to fixed error codes (A§2.2). Verification: a test runs the whole corpus through every tool at DEBUG and asserts that no corpus subject, address or folder name appears in captured stderr. A fake-server corpus with an 8-bit NO and BAD text, folder name and ENVELOPE address, at root DEBUG, yields no `imapclient*` LogRecord (seen through a record factory, since a root handler never sees a non-propagating logger) and empty captured stderr (`capfd`), and the test fails with a WARNING pin; the same 8-bit NO/BAD text appears in no record, no captured output and no surfaced error string.

**T-14 Multi-account confusion.** Mitigation: `account` is required whenever more than one account exists and no `default_account` is set; `message_ref` embeds the account and UIDVALIDITY and is rejected for any other account; per-account connections, locks and credentials; every result names its account. Verification: tests with two accounts on GreenMail (distinct users) that cross-use refs, omit `account`, and confirm one account's failure leaves the other unaffected.

The ceiling is a hard bound: user config (`[limits]`, key below) may lower it but never raise it. Where a row also has a default, a tool argument may choose any value up to the ceiling and the default applies when it is omitted. Rows without a separate default use the ceiling.

Results on breach, defined here only. A server response that breaches an on-read cap is hostile: a literal over its command's literal cap (`L-01`, `L-02`, `L-05`, `L-08` on read), a line over `L-20`, a response over its command's total (`L-26`) or its lines past their total (`L-32`) aborts the read with a typed breach error, discards the session and fails the call with `limit_exceeded` naming the limit, with no reconnect (A§2.2). Not a breach: a single message whose total cannot fit under `L-26` is not fetched, and the result carries a `limit_exceeded` note naming L-26 (A§2.2). The call also fails with `limit_exceeded`, keeping the session, for credential stdout (`L-22`) and the input bounds (`L-23`, `L-24`). `L-28` and `L-29` only bound what the classifier keeps. The timeouts (`L-11` to `L-14`, `L-27`) behave as A§2.1 and A§2.2 state: a credential timeout returns `timeout`; an IMAP connect or read timeout (`L-11`, `L-12`) discards the session and fails the call with `timeout`, with no reconnect; only a dropped connection is re-opened, once per call and never in the login phase; a search scan stops short of `L-13` with `truncated: true` (A§2.6). Every other cap that triggers sets `truncated: true` or adds a `limit_exceeded` note naming the limit ID. Each limit has a test that crosses it.

## 6. Review checklist (per-module gate)

The reviewer confirms, for the threats the task cites: the mitigation exists in code, the listed verification exists as a test and fails when the mitigation is removed, no limit is hard-coded outside `limits.py`, no dependency is added outside the vetted table in `docs/research/library-survey.md` (R§10), imaplib/imapclient private API is used only at the hooks A§2.2 names and is covered by tests on every supported Python minor, and no personal data or secret appears in code, fixtures or docs.
